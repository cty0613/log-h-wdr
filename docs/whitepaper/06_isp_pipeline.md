# 6장. ISP와 듀얼 파이프라인

> 관련 Phase: 4(듀얼 파이프라인) — ⏳ 예정

## 한 줄 요약
ISP(Image Signal Processor)는 RAW 숫자를 "사진"으로 바꾸는 처리 단계의 묶음이다. 이 프로젝트는 공통 앞단을 거친 같은 HDR 데이터에서 **두 갈래**를 만든다. 사람이 바로 보는 표시용(강한 NR, 국소 톤매핑, 8bit)과 정보를 보존하는 보관용(약한 NR, H-Log, 10bit)이다.

---

## 1. 쉬운 비유

필름 사진관의 현상 과정과 같다.
1. 필름의 기본 얼룩 빼기(**BLC**)
2. 렌즈 가장자리가 어두운 것 보정(**LSC**)
3. 점 단위 색 정보를 매끈한 컬러로 채우기(**Demosaic**)
4. 조명 색 빼기, 흰 종이를 흰색으로(**WB**)
5. 센서의 색 감각을 사람의 색 감각으로 번역(**CCM**)
6. 거친 입자 다듬기(**NR**)
7. 너무 밝은 창문과 어두운 방을 한 장에 보이게 인화(**톤매핑**)

보관용은 6번을 살짝만 하고 7번 대신 "나중에 다시 인화할 수 있는 원판"(H-Log)으로 보관한다.

---

## 2. 원리

### 2.1 공통 앞단
```
HDR Bayer (float32, BLC 완료) → LSC → Demosaic → WB → CCM → 선형 RGB
```

**BLC (Black Level Correction)**: 블랙 레벨 64를 빼고 정규화한다(2장). 브래킷 합성 전에 이미 수행했으므로 여기서는 확인만 한다.

**LSC (Lens Shading Correction)**
- 렌즈는 가장자리로 갈수록 빛을 덜 모은다(비네팅, 대략 cos⁴ 법칙). 광각일수록 심하다.
- Pi 튜닝 파일의 ALSC 테이블(32×32 격자 이득)을 화소 위치에 맞게 **bilinear 보간**해 곱한다. 색별(Cr, Cb) 테이블은 색온도로 보간한다.
- 이 카메라(Wide)는 가장자리 이득이 최대 약 4.7배다. **이득을 곱하면 노이즈도 같이 커진다.** 그래서 Pi ISP는 휘도 보정을 65%만 한다(`luminance_strength = 0.65`). 보관용 선형 경로에서 100% 보정을 할지는 Phase 4에서 정한다.
- 튜닝 테이블은 센서 원래 방향 기준이다. 현재 RAW는 상하·좌우 반전 상태이므로 **테이블도 뒤집어 적용**한다(2장의 Bayer 순서와 같은 원인).

**Demosaic (bilinear)**
- 각 화소에 없는 두 색을 같은 색 이웃의 평균으로 채운다.
- 장점: 단순하고 선형이라 분석과 테스트가 쉽다. 단점: 경계에서 지퍼 무늬, 가짜 색, 약한 흐림.
- 표시용과 보관용이 같은 Demosaic을 쓰므로 둘의 비교에는 영향이 적다. 그래서 고급 알고리즘은 범위 밖으로 뒀다.

**WB (White Balance)**
- 조명 색에 따라 R, G, B 신호 비율이 바뀐다. 회색 물체가 R = G = B가 되도록 R, B에 이득을 곱한다(G = 1 기준).
- 이득은 촬영 때 고정한 `colour_gains`(프레임 JSON)를 쓴다.

**CCM (Color Correction Matrix)**
- 센서 컬러 필터의 분광 감도는 사람 눈이나 sRGB 표준과 다르다. 3×3 행렬로 센서 RGB를 표준 RGB로 바꾼다: `out = M·rgb`.
- 각 행의 합이 1이면 흰색이 흰색으로 남는다.
- 색온도별 행렬(튜닝 파일, 2868~7610 K)을 **촬영 색온도로 선형 보간**한다.
- 대각선 밖의 음수 계수는 채널을 빼는 연산이라 노이즈를 키운다. 색 정확도와 노이즈의 트레이드오프다.

### 2.2 NR: guided filter (`nr_guided`)
He 외(2010)의 **guided filter**를 쓴다.
- 작은 창(window) 안에서 출력이 가이드 영상의 **선형 함수**라고 가정한다: `q = a·I + b`.
- `a = cov(I, p) / (var(I) + ε)`, `b = mean(p) − a·mean(I)`.
  - 평탄한 영역(var 작음): a ≈ 0 → 평균값으로 매끈하게.
  - 경계(var 큼): a ≈ 1 → 원래 값 유지.
- **ε가 강도를 정한다.** 노이즈 분산 수준의 ε를 쓰면 "노이즈보다 작은 변화는 지우고 큰 변화는 남긴다"는 의미가 된다.
- 박스 필터(누적합)로 계산해서 창 크기와 무관하게 **O(화소 수)** 다. 같은 목적의 bilateral filter보다 빠르고 경계 근처 역전 현상(gradient reversal)이 없다.

### 2.3 Local 톤매핑 (`tonemap_local`)
HDR 장면(예: 16배 범위)을 8bit 화면에 넣어야 한다. 전체에 같은 곡선을 쓰면(전역 톤매핑) 밝은 창과 어두운 방이 둘 다 밋밋해진다.
1. 휘도의 **로그**를 구한다. 로그 공간에서는 곱셈(조명 × 반사율)이 덧셈이 된다.
2. guided filter로 큰 덩어리(**base** = 조명)와 나머지(**detail** = 질감)로 나눈다.
3. base만 압축한다(예: 범위를 1/4로). detail은 그대로 둔다.
4. 다시 합쳐 지수로 되돌린다.

결과: 조명 차이는 줄고 질감은 살아 있다. Durand & Dorsey(2002)의 bilateral 방식과 같은 구조이고 필터만 guided로 바꿨다. 주의할 점은 경계 주변의 **후광(halo)** 이다. edge-preserving 필터를 쓰는 이유다.

### 2.4 두 갈래
| | 표시용 `DisplayPipeline` | 보관용 `ArchivePipeline` |
|---|---|---|
| NR 강도 | 강함(보기 좋게) | 약함(정보 보존) |
| 톤 | Local 톤매핑 → Rec.709 | H-Log LUT |
| 비트 | 8bit | 10bit |
| 부가 정보 | — | 사이드카 JSONL(프레임별 노출, 노출비, 곡선, CCM, WB, NR 강도…) |
| 되돌리기 | 불가(정보 버림) | 역 LUT로 선형값 복원 가능 |

**사이드카가 필요한 이유**: 보관 영상만으로는 "코드 512가 실제 몇 lux였는지" 알 수 없다. 곡선 종류와 파라미터 해시, 노출비, 색 처리 값을 프레임마다 함께 저장해야 나중에 복원 도구(8장)가 정확히 되돌린다.

## 3. 이 프로젝트에서 ⏳ Phase 4

| 작업 | 검증 |
|---|---|
| LSC, Demosaic, WB, CCM | 블록별 GoogleTest: 상수, 램프, 체커보드 입력 |
| `nr_guided`, `tonemap_local` (OpenMP) | 같은 방식의 해석적 입력 테스트 |
| `apps/process`: 세션/브래킷 폴더 → 표시용 8bit + 보관용 10bit + 사이드카 | 블록별 처리 시간을 `run.json`에 기록 |
| NR 강도 간이 스윕: 게인 2구간(1, 16) × 강도 6단계, SNR·MTF50 | `configs/nr.json`(표시용·보관용 각 2값 + 근거 수치) |

**해석적 입력 테스트의 예**
- 상수 입력 → Demosaic 출력도 상수여야 한다(모든 채널).
- 선형 램프 → bilinear 보간은 선형 함수를 정확히 재현해야 한다.
- 체커보드 → 알려진 주파수 응답(흐림 정도)과 비교.

**MTF50**: 선명도 지표. 경사진 경계(slanted edge)를 찍어 공간 주파수별 대비를 구하고, 대비가 50%로 떨어지는 주파수를 쓴다. NR이 강할수록 SNR은 오르고 MTF50은 떨어진다. 스윕은 이 트레이드오프를 숫자로 보여 준다.

**수락 기준**
- NR을 끈 보관 경로를 decode하면 공통 앞단 선형 출력과 **양자화 오차 수준**에서 일치한다.
- 블록별 GoogleTest 통과.
- 표시용 결과를 Pi ISP 출력과 나란히 놓은 비교 이미지.

## 4. 엔지니어링 포인트

- **노이즈는 처리 단계를 따라 변한다**: 값에 이득 g를 곱하면 분산은 g²배가 된다. LSC(가장자리 최대 4.7배), WB(약 2배), CCM(음수 계수)을 거치면 화소마다 노이즈가 달라진다. 그래서 "H-Log를 어느 지점의 노이즈 분포에 맞추느냐"(센서 중앙? G 채널? CCM 후?)는 Phase 4의 설계 질문이다. 결정과 근거를 `decisions.md`에 남긴다.
- **결정적 병렬화**: OpenMP로 행 단위 `schedule(static)` 분할만 쓰고, 출력에 영향을 주는 병렬 reduction(합계)은 금지한다. 부동소수점 덧셈은 순서에 따라 결과가 달라지기 때문이다. 그래야 스레드 수가 달라도 출력 해시가 같다(8장 수락 기준).
- **메모리 순서**: 화소 루프는 row-major 연속 메모리 순서로 돈다. 캐시 효율이 성능을 좌우한다.
- **처리 시간 기록**: 블록별 시간을 `run.json`에 남겨 병목(대개 guided filter)을 숫자로 본다.
- **기준선을 약하게 만들지 않는다**: 표시용 경로가 못나면 보관용의 이득이 과장된다. 그래서 표시용도 국소 톤매핑과 적정 NR을 갖춘 "정상적인" 경로로 만들고 Pi ISP 출력과 비교한다.

## 면접에서 설명하기

**30초 답변**
> "ISP는 BLC, LSC, Demosaic, WB, CCM의 공통 앞단을 직접 구현하고, 그 뒤를 두 갈래로 나눴습니다. 표시용은 guided filter NR과 base/detail 분리 국소 톤매핑으로 8bit를 만들고, 보관용은 약한 NR 후 H-Log LUT로 10bit와 프레임별 사이드카를 만듭니다. 블록마다 상수·램프·체커보드 입력으로 해석적 테스트를 했고, OpenMP는 결정적으로 병렬화해서 스레드 수와 무관하게 같은 출력을 내게 했습니다."

**예상 질문**
- *처리 순서는 왜 이렇게 했나요?*
  → LSC는 렌즈 광학 효과라 센서 원값에 가장 가까운 곳에서 보정하고, Demosaic 전에 해야 색별 이득을 Bayer 화소에 맞게 적용할 수 있습니다. WB는 CCM 전에 해야 CCM이 기준으로 삼는 "회색 = 같은 값" 상태가 됩니다. NR과 톤매핑은 색 처리가 끝난 선형 RGB에서 합니다.
- *guided filter를 고른 이유는요?*
  → 경계를 보존하면서 계산량이 창 크기와 무관한 O(N)이고, bilateral의 경계 역전 문제가 없습니다. ε가 노이즈 분산과 같은 단위라서 노이즈 모델과 연결해 강도를 정하기도 좋습니다.
- *국소 톤매핑의 halo는 어떻게 다루나요?*
  → base를 edge-preserving 필터로 구해 경계를 넘어 섞이지 않게 하고, 압축 강도와 필터 반경을 조절합니다. 표시용은 보기 좋은 것이 목적이라 halo를 눈으로도 확인합니다.
- *LSC가 노이즈에 주는 영향은요?*
  → 가장자리 이득이 4.7배면 노이즈 표준편차도 4.7배가 됩니다. Pi ISP가 65%만 보정하는 것도 그 때문입니다. 보관 곡선이 어느 지점의 노이즈에 맞춰야 하는지가 여기서 생기는 설계 질문입니다.
- *왜 Python이 아니라 C++로 ISP를 만드나요?*
  → 2304×1296 영상 시퀀스를 반복 처리하고 압축까지 연결해야 해서 성능과 메모리 제어가 필요합니다. 실제 카메라 펌웨어나 ISP 소프트웨어도 C/C++이 표준이라 이식 가능한 형태로 만들었습니다.
