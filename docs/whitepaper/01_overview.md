# 1장. 문제 정의와 프로젝트 전체 그림

> 관련 Phase: 전체

## 한 줄 요약
감시 영상은 "지금 보기 좋은 영상"과 "나중에 증거로 되살릴 수 있는 영상"이 서로 다른 요구를 가진다. 이 프로젝트는 같은 센서 데이터에서 두 영상을 동시에 만들고, 보관 영상의 저장 방식(곡선)을 노이즈 물리에서 유도한다.

---

## 1. 쉬운 비유

창문을 등지고 선 사람을 스마트폰으로 찍으면 둘 중 하나가 된다. 창밖이 하얗게 날아가거나, 사람 얼굴이 시커멓게 묻힌다.
사람 눈은 둘 다 보는데 카메라는 왜 못 할까?

- **센서는 양동이다.** 각 화소는 빛 알갱이(광자)가 만든 전자를 담는 작은 양동이다. 양동이가 넘치면(포화) 얼마나 밝았는지 알 수 없다. 바닥 근처는 잡음에 묻혀 구분이 안 된다. 넘치지 않으면서 바닥 잡음보다는 큰 범위가 **다이내믹 레인지(DR)** 다.
- **저장은 계단이다.** 측정한 밝기를 파일에 쓸 때 1024개(10bit)의 계단 중 하나로 반올림한다. 계단을 어디에 촘촘하게 놓느냐가 "어떤 밝기의 정보를 살리느냐"를 정한다.

이 프로젝트는 양동이 문제(DR 확보)와 계단 문제(DR 보존)를 둘 다 다룬다.

---

## 2. 왜 감시 카메라인가

| 일반 카메라 | 감시 카메라 |
|---|---|
| 찍는 순간 보기 좋으면 된다 | 사건이 난 **뒤에** 영상을 다시 본다 |
| 사람 눈에 맞춘 톤(감마, 톤매핑) | 번호판·얼굴처럼 **특정 정보를 읽어내는 것**이 목적 |
| 하이라이트가 날아가도 "분위기" | 하이라이트에 번호판이 있으면 증거가 사라진다 |
| 파일 크기는 부차적 | 24시간 녹화 → **저장 용량과 압축이 핵심 비용** |

표시용 영상은 화면에 맞게 DR을 **압축**한다(톤매핑). 이 과정에서 버려진 정보는 되살릴 수 없다.
그래서 **보관용으로 DR을 버리지 않는 두 번째 스트림**을 함께 저장하자는 것이 출발점이다. 영화 카메라의 "Log 촬영"과 같은 생각인데, 이 프로젝트는 그 곡선을 감시용 HDR 합성 데이터에 맞게 **물리적으로 유도**한다.

---

## 3. 핵심 용어 세 개

| 용어 | 뜻 | 이 프로젝트에서 |
|---|---|---|
| **DR 확보** | 물리적으로 더 넓은 밝기 범위를 측정하는 것 | 브래킷 합성(실측), DCG(시뮬레이션) — 4장 |
| **DR 보존** | 확보한 범위를 저장할 때 버리지 않는 것 | H-Log 곡선 — 5장 |
| **합성 후 노이즈 분포** | 밝기별로 노이즈가 얼마나 큰지(σ²(x)) | 3·4장에서 측정·모델링, 5장 곡선의 입력 |

## 4. 전체 구조

```
 [Pi 5 + Camera Module 3]                         (Python, Phase 0~1)
   RAW 촬영: 단일 / 브래킷 / 센서 HDR + Pi ISP 출력
            │  .npy + .json (프레임마다)
            ▼
 [DR 확보]                                         (C++, Phase 2)
   브래킷 합성 (Bayer 도메인)   DCG 시뮬레이터
            │  선형 HDR Bayer (float32, 0 ~ R)
            ├──────────────────────────────┐
            ▼                              ▼
 [노이즈 분포 측정·모델]  (Python)    [공통 ISP 앞단]  (C++, Phase 4)
   σ²(x) 구간별 (a_i, b_i)          LSC → Demosaic → WB → CCM
            │                              │
            ▼                       ┌──────┴───────┐
 [곡선 파라미터 계산] (Python, P3)   ▼              ▼
   H-Log 상수, 필요 비트 ────▶ [보관용]        [표시용]
                                 NR(약)         NR(강)
                                 H-Log LUT      Local 톤매핑
                                 10bit+사이드카  Rec.709 8bit
                                    │
                                    ▼
                         [HEVC 압축 / 복원] (C++, Phase 5~6)
                                    │
                                    ▼
                         [평가] 복원 SNR, 밴딩, 번호판 OCR (Python)
```

---

## 5. 검증할 가설

| 가설 | 내용 | 확인 방법 | Phase |
|---|---|---|---|
| **H1** | 합성 후 노이즈에 맞춘 H-Log는 같은 비트에서 단일 노출 기준 곡선, S-Log3, HLG보다 양자화 손실이 작다 | 밝기별 R(x) = 양자화 간격 / 노이즈 비교 | 3 |
| **H2** | 확보한 DR에 따라 필요한 비트 수가 정량적으로 정해진다 | 브래킷 R = 1~64에 대해 ⌈log₂N⌉ 계산 | 3 |
| **H3** | HEVC 압축(QP 22~37) 후에도 보관 영상의 복원 이득이 일정 QP까지 유지된다 | 복원 SNR, OCR 정확도 vs QP | 5, 6 |

**반대 결론도 결과다.** 예를 들어 "QP 37에서는 곡선 종류와 무관하게 이득이 사라진다"는 것도 유용한 결론이다. 그래서 비교 대상(표시용 경로, 비교 곡선)을 일부러 약하게 만들지 않는다. 면접에서 이 점을 말할 수 있으면 좋다(10장).

## 7. 하지 않는 것과 그 이유

범위를 줄이는 것도 엔지니어링 판단이다. 면접에서 "왜 이건 안 했나요?"라는 질문에 답할 수 있어야 한다.

| 하지 않는 것 | 이유 |
|---|---|
| ColorChecker로 CCM·LSC 직접 보정 | 핵심 아이디어(곡선)와 무관. Pi 튜닝 파일 값으로 충분 |
| 고급 Demosaic (Malvar 등) | 곡선·압축 비교는 표시·보관 경로 모두 같은 Demosaic을 쓰므로 비교에 영향이 적다 |
| 움직이는 장면의 브래킷 합성 | 움직임 보상(고스트 제거)은 별도의 큰 주제. 정지 장면에서 원리를 먼저 검증 |
| 실제 DCG 하드웨어 | IMX708/Pi에서 제어할 수 없음. 가정값을 명시한 시뮬레이션으로 대체 |
| pybind11 연동 | Python↔C++를 파일로만 연결하면 경계가 단순하고 재현이 쉽다(9장) |

## 면접에서 설명하기

**30초 답변**
> "감시 카메라는 역광 번호판처럼 DR이 넓은 장면을 찍고, 사건이 난 뒤에 영상을 다시 봅니다. 표시용으로 톤매핑하면 정보가 버려지기 때문에, 같은 데이터로 보관용 10bit 스트림을 따로 만들었습니다. 보관용 곡선은 센서 노이즈 측정값에서 유도해서 노이즈보다 작은 차이에는 코드를 쓰지 않도록 했고, HDR 합성 방식마다 노이즈 모양이 달라서 곡선도 합성 방식에 맞췄습니다. 마지막으로 HEVC 압축 후 번호판 인식률로 이득을 검증했습니다."

**예상 질문**
- *왜 그냥 RAW를 저장하지 않나요?*
  → RAW는 화소당 10~16bit이고 Bayer라서 일반 영상 코덱으로 효율적으로 압축하기 어렵습니다. 24시간 녹화에서는 저장 비용이 핵심입니다. 표준 HEVC 10bit에 넣을 수 있는 형태로 정보를 보존하는 것이 실용적인 목표입니다.
- *S-Log3 같은 기존 Log 곡선을 쓰면 되지 않나요?*
  → 기존 곡선은 특정 센서와 단일 노출을 가정하고, "밝기에 비례하는 노이즈"에 가까운 모양입니다. 실제 센서 노이즈는 샷 노이즈(√밝기에 비례)와 판독 노이즈로 이뤄지고, HDR 합성을 하면 경계에서 노이즈가 계단처럼 뜁니다. 그 모양에 곡선을 맞추면 같은 비트에서 손실이 줄어드는지가 H1 가설이고, 기존 곡선을 비교군으로 직접 측정합니다.
