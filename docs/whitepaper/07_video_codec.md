> 관련 Phase: 5(C++ 코덱과 압축 실험) — ⏳ 예정

## 한 줄 요약
감시 영상은 저장하려면 수백 배로 압축해야 하고, 압축은 정보를 버린다. H-Log로 넣은 하이라이트·섀도우 정보가 **HEVC 압축 뒤에도 남는지**, 몇 QP까지 남는지를 측정하는 것이 H3 가설이다.

## 1. 쉬운 비유

긴 편지를 전보로 보낸다고 하자.
- "지난 장면과 같음, 단 왼쪽 위 차가 3칸 이동"처럼 **이전 프레임을 참조해 차이만** 보낸다(예측).
- 남은 차이도 "큰 흐름"과 "자잘한 무늬"로 나눠서, 자잘한 무늬는 덜 정확하게 적는다(변환과 양자화).
- **QP는 "얼마나 대충 적을지"의 손잡이**다. 올리면 파일은 작아지고 자잘한 정보가 사라진다.

센서 노이즈는 무작위라 예측이 안 되고 "자잘한 무늬"로 분류된다. 그래서 노이즈는 비트를 많이 먹고, QP를 올리면 가장 먼저 지워진다. 노이즈만큼 작은 *진짜 정보*(어두운 곳의 번호판 글자)도 같이 지워질 수 있다.

## 2. 원리

### 2.1 왜 압축이 필수인가
2304×1296, 10bit, 4:2:0, 30 fps 무압축이면
```
2304 × 1296 × 1.5 샘플 × 10 bit × 30 fps ≈ 1.34 Gbit/s  (하루 약 14.5 TB)
```
HEVC는 이것을 수 Mbit/s로 줄인다. 수백 배다. 24시간 녹화에서 압축 후의 화질이 실제 쓸모를 정한다.

### 2.2 RGB → YCbCr, 4:2:0
코덱은 RGB가 아니라 **밝기(Y) + 색차(Cb, Cr)** 를 받는다. 사람 눈은 색 해상도에 둔감해서 색차를 줄여도 티가 덜 나기 때문이다.

BT.709 계수(Kr = 0.2126, Kb = 0.0722):
```
Y  = 0.2126·R + 0.7152·G + 0.0722·B
Cb = (B − Y) / 1.8556
Cr = (R − Y) / 1.5748
```
- **Range**: full range(0~1023 전체 사용)와 limited range(10bit Y 64~940, C 64~960)가 있다. 어느 쪽인지 틀리면 밝기와 대비가 조용히 틀어진다. 이 프로젝트는 **full range를 명시**하고 그대로 기록한다.
- **4:2:0**: Cb, Cr을 가로·세로 절반 해상도로 줄인다. 줄이는 필터(다운샘플)와 되살리는 필터(업샘플), 색차 샘플 위치(chroma siting)를 **코드와 문서에 명시**한다.
- 이 변환은 H-Log로 이미 휘어진 RGB에 적용된다. 일반 방송 영상(감마 RGB → YCbCr)과 같은 관례다.

**왜 swscale(FFmpeg 변환 라이브러리)를 쓰지 않나**: 기본 필터, 범위, 반올림이 버전과 옵션에 따라 달라진다. 실험의 오차 원인을 분리하려면 변환을 직접 구현해서 모든 규칙이 보이게 해야 한다.

### 2.3 HEVC(H.265)가 하는 일
| 단계 | 하는 일 | 정보 손실 |
|---|---|---|
| 블록 분할 | 화면을 최대 64×64(CTU)부터 작은 블록으로 쪼갬 | 없음 |
| 예측 | 화면 안(intra) 또는 이전 프레임(inter)에서 블록을 예측 | 없음 |
| 잔차 변환 | 예측과의 차이를 정수 DCT 계열로 주파수 성분으로 바꿈 | 없음 |
| **양자화** | 주파수 성분을 Qstep으로 나눠 반올림 | **여기서 손실** |
| 엔트로피 부호화 | CABAC으로 비트열을 압축 | 없음 |
| 루프 필터 | 디블로킹, SAO로 블록 경계와 오차를 다듬음 | 보정 |

**QP와 Qstep**: Qstep ≈ 2^((QP − 4)/6). QP가 **6 오르면 양자화 간격이 2배**가 된다. QP 22 → 37은 15 차이라 약 5.7배 거칠어진다.
QP {22, 27, 32, 37}은 HEVC 표준화(JCT-VC) 공통 시험 조건에서 쓰는 범위다. 이 프로젝트는 {22, 30, 37}로 그 범위를 덮는다.

**10bit 프로파일(Main10)**: 10bit 입력을 그대로 다룬다. 8bit로 줄이면 계단이 4배 거칠어져 매끈한 하늘에 **밴딩**(줄무늬 경계)이 보인다.

### 2.4 곡선과 압축 오차의 관계 (이 프로젝트의 핵심 연결고리)
코덱 오차는 대략 **코드 공간에서** 생긴다. 코드 오차 ε가 선형값에서 얼마인지는 곡선 기울기로 정해진다.
```
선형 오차 ≈ ε / C′(x)
```
H-Log는 C′(x) ∝ 1/σ(x)이므로 **선형 오차 ∝ σ(x)**. 즉 압축 오차가 모든 밝기에서 "그 밝기의 센서 노이즈에 비례"하게 퍼진다. 다른 곡선은 어떤 밝기에서는 노이즈보다 훨씬 큰 오차를, 다른 밝기에서는 훨씬 작은 오차를 낸다.
이것이 "노이즈에 맞춘 곡선이 압축 후에도 유리할 것"이라는 H3의 근거이고, 측정으로 확인할 대상이다.

**반대 방향의 힘**: 노이즈는 예측이 안 돼서 비트를 많이 먹는다. 보관용 NR을 약하게 하면 정보는 남지만 같은 QP에서 비트레이트가 오르거나, 같은 비트레이트에서 QP가 올라간다. **NR 강도와 QP는 같이 봐야 하는 트레이드오프**다.

## 4. 엔지니어링 포인트

- **라이브러리를 직접 링크**: CLI(`ffmpeg` 명령)가 아니라 libavcodec API를 C++에서 직접 쓴다. 프레임 단위로 데이터를 넣고 빼면서 변환 규칙과 메타데이터를 통제할 수 있다.
- **인코더의 "보기 좋게" 옵션을 조심한다**: x265에는 사람 눈 기준으로 비트를 재분배하는 기능(적응 양자화, psycho-visual 최적화)이 있다. 측정 실험에서는 곡선 간 비교를 흐릴 수 있어, 어떤 값으로 돌렸는지를 반드시 기록하고 비교 조건을 같게 둔다.
- **QP 0은 완전 무손실이 아니다**: HEVC의 진짜 무손실은 변환·양자화를 건너뛰는 별도 모드다. 왕복 테스트의 오차 한계는 이 차이를 알고 정한다.
- **버전 고정과 라이선스**: FFmpeg 9.0.2와 x265 4.3을 vcpkg baseline으로 고정했다. x265를 정적 링크하면 결과물이 GPL이 된다는 점도 기록했다.
- **비교 공정성**: 모든 곡선이 같은 장면, 같은 QP, 같은 인코더 설정, 같은 YCbCr 변환을 쓴다. 다른 것은 곡선 하나뿐이어야 한다.

## 면접에서 설명하기

**30초 답변**
> "보관 영상을 libavcodec과 libx265로 C++에서 직접 인코딩했고, RGB↔YCbCr 변환과 4:2:0 필터는 오차 원인을 분리하려고 직접 구현했습니다. 곡선 4종과 8bit 대조군을 QP 22, 30, 37로 압축한 뒤 역변환해서 선형 원본 대비 영역별 복원 SNR과 밴딩을 쟀습니다. 코덱 오차는 코드 공간에서 생기기 때문에, 노이즈에 맞춘 곡선을 쓰면 압축 오차가 밝기마다 노이즈에 비례해 퍼진다는 것이 가설의 근거입니다."

**예상 질문**
- *QP가 6 오르면 무슨 일이 생기나요?*
  → 양자화 간격이 2배가 됩니다. 고주파 성분부터 0이 되어 노이즈와 미세 질감이 사라지고 비트레이트가 줄어듭니다.
- *왜 4:2:0인가요? 4:4:4면 더 좋지 않나요?*
  → 감시 시스템과 하드웨어 디코더의 호환성 때문에 4:2:0이 사실상 표준입니다. 실제 배포 조건에서 이득이 남는지를 보는 것이 목적이라 4:2:0으로 시험합니다. 색 경계 손실은 업샘플 필터를 명시해 재현 가능하게 했습니다.
- *full range와 limited range가 왜 중요하나요?*
  → 인코더·디코더·플레이어 중 하나라도 다르게 해석하면 검정과 흰색이 들뜨거나 잘립니다. 측정 실험에서는 조용한 오차가 제일 위험해서 명시하고 기록합니다.
- *노이즈를 남기면 압축 효율이 떨어지지 않나요?*
  → 그렇습니다. 노이즈는 예측이 안 돼서 비트를 많이 먹습니다. 그래서 보관용 NR 강도와 QP를 같이 보고, 같은 비트레이트에서 복원 SNR을 비교하는 것이 공정한 비교입니다.
- *8bit 대조군을 넣은 이유는요?*
  → "10bit라서 좋은 것"과 "곡선이 좋아서 좋은 것"을 분리하기 위해서입니다. 같은 H-Log를 8bit로 넣었을 때의 손실을 보면 비트 수의 기여를 따로 알 수 있습니다.
