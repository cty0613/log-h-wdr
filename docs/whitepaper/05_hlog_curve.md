# 5장. 전달 곡선과 H-Log 설계

> 관련 Phase: 3(HDR 대응 H-Log, 핵심) — ⏳ 예정

## 한 줄 요약
저장 비트의 계단을 **노이즈 크기에 비례하는 간격**으로 놓으면, 모든 밝기에서 "양자화로 잃는 정보 / 원래 있던 노이즈"의 비율이 똑같아진다. 이 조건을 수식으로 풀면 곡선 `C(x) = k·∫dx/σ(x)`가 나오고, HDR 합성 후의 구간별 노이즈 분포를 넣으면 그대로 **H-Log**가 된다.

---

## 1. 쉬운 비유

**자의 눈금 간격 정하기.** 손이 떨리는 사람이 길이를 잰다고 하자. 손 떨림이 ±1 mm면 0.01 mm 눈금은 소용이 없다. 반대로 눈금이 5 mm 간격이면 손이 아무리 정확해도 5 mm 안의 차이는 기록되지 않는다.
**가장 효율적인 자는 눈금 간격이 손 떨림 크기에 맞춰진 자다.**

센서는 밝기마다 "손 떨림"(노이즈)이 다르다. 어두운 곳은 작고 밝은 곳은 크다. HDR 합성 경계에서는 갑자기 커진다. 그래서 1024개 눈금을 **노이즈가 작은 곳엔 촘촘하게, 큰 곳엔 성기게** 배치한다. 이 눈금 배치 규칙이 전달 곡선이고, H-Log는 실제로 측정한 노이즈에 맞춰 눈금을 놓은 자다.

---

## 2. 원리

### 2.1 왜 선형 저장이 나쁜가
선형 10bit로 저장하면 계단 간격 Δx가 모든 밝기에서 같다(1/1023).
- 밝은 곳: 노이즈가 커서 계단이 노이즈보다 훨씬 작다 → 코드 낭비.
- 어두운 곳: 노이즈가 작아서 계단이 노이즈보다 크다 → 정보 손실, 밴딩.

그래서 거의 모든 영상은 **휘어진 곡선**(감마, Log)을 거쳐 저장한다.

### 2.2 표시용 곡선과 보관용 곡선은 목적이 다르다
| | 표시용 (Rec.709 감마 등) | 보관용 (H-Log) |
|---|---|---|
| 최종 소비자 | 사람 눈 | 나중의 처리(노출 보정, 복원, OCR) |
| 맞추는 기준 | 사람의 밝기 지각(베버-페히너: 상대 차이를 느낌) | 센서 노이즈(물리) |
| 질문 | "사람이 이 차이를 볼 수 있나?" | "이 차이가 노이즈보다 큰 실제 정보인가?" |

보관 영상은 나중에 밝기를 몇 stop씩 올리거나 내린다. 지각 기준으로 아낀 섀도우 코드가 그때 밴딩으로 드러난다. 그래서 보관용은 **노이즈 기준**이 맞다는 것이 이 프로젝트의 관점이다.

### 2.3 양자화 지표 R(x)
곡선 C(x)가 선형값 x를 [0, 1] 코드로 바꾸고, bits 비트로 양자화한다고 하자.
- 코드 1단계에 해당하는 선형 간격: `Δx = (1 / (2^bits − 1)) / C′(x)`
- 지표: **`R(x) = Δx / σ(x)`** = 양자화 계단 / 노이즈 표준편차

양자화 오차는 계단 안에서 균일하므로 표준편차가 `Δx/√12 ≈ 0.29·Δx`다. R = 1이면 전체 노이즈가 `√(1 + 1/12) ≈ 1.04`배, 즉 **4% 늘어난다.** 그래서 R ≤ 1이면 양자화 손실은 "원래 노이즈의 몇 %" 수준으로 작다.

### 2.4 노이즈 매칭 곡선의 유도
모든 x에서 R(x)를 같게 만들고 싶다.
```
R(x) = 1 / ((2^bits − 1)·C′(x)·σ(x)) = 상수   ⇔   C′(x) ∝ 1/σ(x)
```
적분하면
```
C(x) = k·∫₀ˣ dt/σ(t),     k = 1 / ∫₀^{x_max} dt/σ(t)   (C(x_max) = 1)
```
- 이 곡선을 거친 뒤에는 노이즈가 **모든 밝기에서 코드 단위로 같은 크기** k가 된다. 통계학에서 **분산 안정화 변환**(variance-stabilizing transform)이라 부르는 것과 같은 원리다. 포아송 데이터에 쓰는 Anscombe 변환 `2√(x + 3/8)`이 대표적인 예다.
- 같은 비트에서 **가장 나쁜 밝기의 R을 가장 작게** 만드는 배치다. 한 곳의 R을 줄이려면 다른 곳 계단을 넓혀야 하기 때문이다(최대값 최소화).

### 2.5 구간별 닫힌 형태
노이즈 분포가 구간별로 `σ²(x) = aᵢ·x + bᵢ`(3·4장)이므로 적분이 닫힌 형태로 풀린다. 구간 i (x ∈ [xᵢ, xᵢ₊₁)):
```
aᵢ > 0:  ∫ dt/√(aᵢt + bᵢ) = (2/aᵢ)·(√(aᵢx + bᵢ) − √(aᵢxᵢ + bᵢ))
aᵢ = 0:  (x − xᵢ)/√bᵢ                                         (판독 노이즈만 있는 경우)
```
- 각 구간의 모양은 **제곱근에 가까운 곡선**이다. 샷 노이즈가 √x에 비례하기 때문이다.
- 구간 경계에서 C의 **값은 연속**이고 **기울기는 불연속**이다. 브래킷 경계에서 노이즈가 √R배 뛰므로 기울기도 1/√R배로 꺾인다. 노이즈 점프를 그대로 반영하는 것이 설계 의도다.
- 역함수: C 값으로 구간을 찾은 뒤 위 식을 x에 대해 풀면 닫힌 형태로 계산된다(반복 계산 불필요).

**왜 "Log"라고 부르나**: 업계에서 넓은 범위를 담는 촬영용 곡선을 Log 계열이라 부르는 관례를 따른 이름이다. 수학적으로 H-Log는 순수 로그가 아니라 구간별 제곱근 곡선이다. 순수 로그는 "노이즈가 밝기에 비례"(σ ∝ x)를 가정한 곡선이고, 실제 센서의 샷 노이즈(σ ∝ √x)와는 다르다. 이 차이가 H1 가설의 근거다.

### 2.6 N과 필요 비트
노이즈 매칭 곡선에서는 R이 상수다.
```
R = N / (2^bits − 1),    N = ∫₀^{x_max} dx/σ(x)
```
- **N = 측정 범위 안에서 노이즈 1σ 간격으로 구분할 수 있는 단계 수**다.
- R ≤ 1 조건이면 **필요 비트 = ⌈log₂N⌉**. 이것이 H2 가설의 계산식이다.

**예시 계산** (5.4 스키마 예시 값 a = 0.0012, b = 2e-6을 넣은 것. 실측이 아니므로 Phase 3에서 실측값으로 바꾼다.)
| 경우 | N | log₂N | ⌈log₂N⌉ |
|---|---|---|---|
| 단일 노출 (x_max = 1) | 55.4 | 5.79 | 6 |
| 브래킷 R = 4 | 82.8 | 6.37 | 7 |
| 브래킷 R = 16 | 96.4 | 6.59 | 7 |
| 브래킷 R = 64 | 103.0 | 6.69 | 7 |

이 예시에서 두 가지를 읽을 수 있다.
1. **브래킷으로 범위를 R배 넓혀도 N은 조금만 늘어난다.** 짧은 노출 구간은 노이즈가 커서 구분 가능한 단계가 적기 때문이다. 샷 노이즈만 있다면 한 노출이 보탤 수 있는 단계 수는 약 `2√(포화 전자 수)`로 제한된다(위 식에서 R → ∞ 극한이 `2/√a`). **범위(stop)와 정보량(단계 수)은 다르다**는 것이 핵심 통찰이다.
2. 필요 비트가 10bit보다 작게 나와도 10bit가 낭비는 아니다. R ≤ 1은 *양자화만* 고려한 하한이다. 10bit에서 R = N/1023 ≈ 0.1이면 **압축 오차(7장)와 복원 시 밝기 보정의 여유**가 된다. 얼마의 여유가 필요한지는 Phase 5에서 측정으로 답한다.

### 2.7 비교 곡선
| 곡선 | 식 (입력 L, 출력 V ∈ [0,1]) | 설계 기준 | 출처 |
|---|---|---|---|
| **Rec.709** OETF | L < 0.018: V = 4.5L / 그 외: V = 1.099·L^0.45 − 0.099 | SDR 방송, 지각(감마) | ITU-R BT.709 |
| **HLG** | 0 ≤ E ≤ 1/12: V = √(3E) / 그 외: V = a·ln(12E − b) + c (a = 0.17883277, b = 1 − 4a, c = 0.5 − a·ln(4a)) | HDR 방송, SDR 호환 | ITU-R BT.2100 |
| **S-Log3** | in ≥ 0.01125: V = (420 + 261.5·log₁₀((in + 0.01)/0.19)) / 1023 / 그 외: V = (in·(171.2102946929 − 95)/0.01125 + 95) / 1023 | 시네마 촬영, 18% 회색 기준 | Sony 공개 문서 |
| **H-Log** | C(x) = k·∫dx/σ(x) | 센서·합성 노이즈(물리) | 이 프로젝트 |

- HLG의 아래쪽 절반이 **√E**라는 점이 흥미롭다. 어두운 영역에서는 샷 노이즈와 같은 모양이다. 위쪽은 로그다.
- S-Log3는 18% 회색을 코드 420(10bit)에 두고, 입력 약 38까지(18% 회색의 약 200배) 담는다.
- **공정한 비교 규칙**: 곡선마다 정의역이 다르다(Rec.709는 1.0, S-Log3는 약 38). 합성 결과의 x_max를 각 곡선의 정의역 상한에 맞추는 규칙을 Phase 3에서 정해 `decisions.md`에 쓴다. 비교군에 불리한 스케일을 고르면 결론이 무의미해진다.

### 2.8 고정소수점 LUT
실제 카메라 칩(ISP 하드웨어, 임베디드)에서는 화소마다 제곱근·로그를 float로 계산하지 않는다. **표(LUT)를 미리 만들어 찾기만** 한다.
- 정방향: x ∈ [0, x_max] → uint16 인덱스(65536 엔트리, 균등 간격) → 10bit 코드.
- 역방향: 10bit 코드(1024 엔트리) → float 선형값.
- 반올림은 round-half-up, 범위 밖은 포화. 규칙은 `docs/fixed_point.md`와 `fixed.hpp`가 항상 일치해야 한다.
- 수락 기준: LUT vs float 최대 **1 LSB**(10bit 코드 1단계).

**확인할 위험**: 인덱스가 x에 대해 균등하므로, 곡선이 가장 가파른 x = 0 근처에서 인덱스 한 칸이 여러 코드에 걸칠 수 있다. 예시 값(N ≈ 96, b = 2e-6, x_max = 16)으로 계산하면 x = 0 근처에서 인덱스 한 칸이 약 1.8 LSB다. 인덱스 반올림 오차(반 칸)가 약 0.9 LSB이므로 1 LSB 기준에 가깝다. Phase 3에서 실측 값으로 오차 표를 만들어 확인하고, 넘으면 엔트리 사이 선형 보간이나 비균등 인덱스 같은 선택지를 `decisions.md`에 정리한다.

## 4. 엔지니어링 포인트

- **파라미터 계산과 적용의 분리**: 곡선 상수(k, 구간 경계, 구간별 오프셋)는 Python이 계산해 JSON으로 넘기고, C++은 받아서 적용만 한다. 같은 JSON을 쓰면 실험 재현이 보장된다.
- **외부 수식은 기준값 테스트로 고정**: Rec.709, HLG, S-Log3는 표준 문서의 식을 주석에 출처와 함께 쓰고, 알려진 입력/출력 쌍으로 테스트한다. 오타 하나가 결론을 뒤집기 때문이다.
- **단조성과 왕복 테스트**: 곡선은 증가 함수여야 하고, encode → decode가 양자화 오차 안에서 원래 값으로 돌아와야 한다. 구간 경계 바로 앞뒤의 값을 반드시 테스트에 넣는다(기울기가 꺾이는 곳에서 버그가 난다).
- **`-ffast-math` 금지**: 이 옵션은 연산 순서를 바꾸고 NaN/무한대 처리를 생략한다. 그러면 Python 기준 모델과의 1e-5 일치와 플랫폼 간 결과 동일성이 깨진다.
- **반올림 규칙 명시**: C++의 기본 float→int 변환은 0 방향 버림이다. round-half-up을 직접 구현하고 문서와 일치시킨다. 작은 규칙 차이가 1 LSB 오차가 된다.

## 면접에서 설명하기

**30초 답변**
> "저장 곡선을 사람 눈이 아니라 센서 노이즈 기준으로 설계했습니다. 양자화 계단을 노이즈 표준편차에 비례하게 놓으면 모든 밝기에서 양자화 손실 비율이 같아지는데, 그 조건을 풀면 1/σ(x)를 적분한 곡선이 나옵니다. HDR 합성 후 노이즈가 구간별로 aᵢx + bᵢ라서 닫힌 형태로 풀리고, 경계에서는 노이즈 점프만큼 기울기가 꺾입니다. 이 적분값 N이 구분 가능한 단계 수라서 필요 비트를 log₂N으로 계산할 수 있습니다."

**예상 질문**
- *왜 σ에 비례하는 계단이 최적인가요?*
  → 기준을 "가장 나쁜 밝기의 양자화 손실 최소화"로 두면, 한 곳의 계단을 줄이려면 다른 곳을 늘려야 하므로 모든 곳에서 R이 같을 때가 최적입니다. 통계에서 분산 안정화 변환과 같은 원리입니다.
- *기울기 불연속이 문제가 되지 않나요?*
  → 값은 연속이라 영상에 단차는 생기지 않습니다. 기울기가 꺾이는 것은 실제 노이즈가 경계에서 뛰기 때문이고, 꺾지 않으면 경계 위쪽에 노이즈보다 촘촘한 계단을 낭비하게 됩니다. 다만 압축 후 경계 근처의 거동은 Phase 5에서 따로 확인합니다.
- *S-Log3보다 좋다는 건 어떻게 공정하게 비교하나요?*
  → 같은 비트, 같은 입력 범위에서 R(x)를 비교합니다. 곡선마다 정의역이 달라서 입력 스케일 규칙을 먼저 정하고 문서에 남깁니다. 비교군에 불리한 스케일을 고르지 않는 것이 중요합니다.
- *필요 비트가 7bit로 나오면 10bit는 필요 없나요?*
  → R ≤ 1은 양자화만 고려한 하한입니다. 실제로는 압축 오차와 나중의 밝기 보정이 더해지므로 여유가 필요하고, 그 여유가 얼마인지는 압축 실험으로 측정합니다. 또 범위를 넓혀도 정보량은 √(전자 수)로 제한되어 N이 천천히 늘어난다는 것이 계산에서 나온 통찰입니다.
- *왜 LUT로 바꾸나요?*
  → 하드웨어나 임베디드 ISP는 화소마다 제곱근을 계산하지 않고 표를 찾습니다. 실제 제품으로 갈 수 있는 형태인지, 그때 오차가 1 LSB 안인지를 검증하는 것입니다. 균등 인덱스는 곡선이 가파른 어두운 영역에서 해상도가 부족해질 수 있어서 오차 표로 확인합니다.
