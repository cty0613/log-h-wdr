# 9장. 엔지니어링 원칙: 검증, 재현성, 하드웨어 다루기

> 관련 Phase: 전체 (Phase 0 사례 반영 ✅)

## 한 줄 요약
연구 결과가 믿을 만하려면 **(1) 코드가 의도한 수식대로 계산하는지 검증되고, (2) 누가 언제 돌려도 같은 결과가 나오고, (3) 하드웨어 동작을 추측이 아니라 측정으로 알아야 한다.** 이 프로젝트의 구조와 규칙은 대부분 이 세 가지를 위한 것이다.

---

## 1. 쉬운 비유

실험실 노트를 생각하면 된다.
- 저울을 쓰기 전에 표준 추로 영점을 확인한다 → **기준 모델로 C++ 검증**
- 시약의 제조번호를 적는다 → **라이브러리 버전 고정, git commit 기록**
- 실험 조건과 결과를 같은 쪽에 적는다 → **결과 폴더마다 `run.json`과 config 사본**
- 장비 설명서를 믿지 않고 직접 재 본다 → **Pi 동작 실측(2장)**
- 실패한 시도도 적는다 → **`decisions.md`에 버린 대안까지 기록**

## 2. 언어 경계: Python과 C++

| 역할 | 언어 | 이유 |
|---|---|---|
| 촬영(Pi), 파라미터 계산, 통계, 실험 관리, 그래프 | Python | 빠른 반복, NumPy/matplotlib, Picamera2가 Python |
| 화소 처리(합성, ISP, 곡선 적용), 코덱 | C++20 | 성능, 메모리 제어, 실제 카메라 SW와 같은 형태 |

**경계 규칙**
- **파라미터 계산은 Python, 파라미터 적용은 C++.** 곡선 상수, NR 강도 같은 값은 `configs/*.json`으로 넘긴다.
- 둘은 **파일(npy, JSON, 영상)과 CLI 호출로만** 연결한다. 바인딩(pybind11)을 쓰지 않는다.
  - 장점: 중간 결과가 모두 파일로 남아 확인할 수 있다. C++ 앱을 Python 없이 단독으로 실행·디버깅할 수 있다. 빌드 의존성이 단순하다.
  - 대가: 파일 I/O 비용. 이 프로젝트 규모에서는 무시할 수 있다.
- Python은 `cli.run_cpp(app, **args)` **하나로만** C++를 부른다. 실패하면 stderr를 포함한 예외를 던진다. 호출 경로가 하나라서 로깅, 경로 탐색, 오류 처리가 한곳에 모인다.
- Python 쪽에 화소 처리 로직을 새로 만들지 않는다. 예외는 `ref/`의 **기준 모델**(검증 전용, 실험 경로에서 사용 금지)이다.

## 3. 검증 전략

### 3.1 기준 모델 대조 (핵심 블록)
| 블록 | 기준 | 허용 오차 | 근거 |
|---|---|---|---|
| 곡선 4종 C++ float | Python float64 기준 모델 | 상대오차 ≤ 1e-5 | float32 유효숫자 약 7자리 + 연산 누적 여유 |
| H-Log 고정소수점 LUT | C++ float | 10bit 코드 최대 1 LSB | 정수화 반올림의 불가피한 오차 |
| 브래킷 합성 | Python 기준 모델 | ≤ 1e-5 | 위와 같음 |
| DCG 시뮬레이터 | 해석적 평균·분산 | 1e5 샘플에서 분산 ±3% | 분산 추정 표준오차 ≈ 0.45% |

**왜 Python 기준 모델인가**: 최적화된 C++(병렬, float32, 메모리 재사용)는 버그가 숨기 쉽다. 같은 수식을 가장 단순하게 float64로 쓴 코드와 비교하면 "수식 오류"와 "구현 오류"를 분리할 수 있다.

### 3.2 해석적 입력 테스트 (기타 블록)
Demosaic, NR, 톤매핑, CCM처럼 기준 모델을 따로 두지 않는 블록은 **답을 미리 아는 입력**으로 테스트한다.
- 상수 → 상수가 나와야 한다.
- 선형 램프 → bilinear 보간은 정확히 재현해야 한다.
- 체커보드 → 알려진 주파수 응답.

### 3.3 교차 검증의 실제 예 ✅ Phase 0
C++ npy 로더와 NumPy가 **바이트 단위로 같은지** 15개 케이스로 확인했다(`tests/py/test_npy_crosscheck.py`).
- 케이스: 10bit RAW 크기의 uint16, 1×1, float32 3채널, 특수 float(±0, ±inf, NaN, subnormal), HDR 범위 float, npy 포맷 v1/v2/v3, 비연속 배열.
- 거부 확인: big-endian, int16, 1차원, Fortran 순서는 오류가 나야 한다.
- **테스트를 테스트했다**: C++ 로더에 1비트 오류를 일부러 넣으면 10개 케이스가 실패하는지 확인했다(mutation test). 통과만 하는 테스트는 아무것도 증명하지 않는다.
- Pi에서 찍은 실제 RAW 샘플로도 한 번 더 확인했다.

### 3.4 수락 기준
각 Phase는 **자동으로 검사되는 수락 기준**(테스트 또는 스크립트 출력)이 있어야 끝난다. 기준을 못 넘으면 **기준을 바꾸지 않고** 원인과 선택지를 `decisions.md`에 정리해 결정한다.

## 4. 재현성

| 장치 | 내용 |
|---|---|
| 의존성 버전 고정 | vcpkg manifest + `builtin-baseline`(커밋 해시). FFmpeg 9.0.2, x265 4.3, OpenCV 4.14.0, Eigen 3.5.0, nlohmann_json 3.12.0 |
| 빌드 프리셋 | `CMakePresets.json`: release(-O3, OpenMP), debug. 같은 명령으로 같은 빌드 |
| `run.json` | 모든 C++ CLI가 출력 폴더에 버전, git commit, dirty 여부, 파라미터, 처리 시간, 라이브러리 버전을 남긴다 |
| 실험 스크립트 | config yaml만 인자로 받는다. 결과 폴더에 config 사본, git commit, C++ `run.json`들을 모은다 |
| 무작위성 | `np.random.Generator`를 인자로 받고 seed는 config에 둔다 |
| Pi 작업 | `pi_job.json`에 스크립트, 인자, 시각, 종료 코드, git commit, capture/ 수정 여부 |
| 결정 기록 | `decisions.md`: 날짜, 결정, 근거 수치, **버린 대안** |

**결정적 계산**
- `-ffast-math` 금지: 연산 순서 재배열, NaN/무한대 처리 생략 → 기준 모델 일치와 플랫폼 간 동일성이 깨진다.
- OpenMP는 행 단위 `schedule(static)`, 출력에 영향을 주는 병렬 reduction 금지 → 스레드 수와 무관하게 같은 비트.
- 고정소수점 반올림은 round-half-up으로 명시하고 문서(`fixed_point.md`)와 코드(`fixed.hpp`)를 일치시킨다.

## 5. 하드웨어 다루기: 추측하지 않고 측정한다 ✅ Phase 0

**규칙**: 모르는 하드웨어 동작은 측정 스크립트(`capture/pi_probe.py`)를 먼저 만들어 확인하고, 결과를 `pi_notes.md`에 날짜와 명령과 함께 기록한다.

이 규칙이 실제로 잡아낸 것:

| 추측했다면 | 실측 | 놓쳤다면 생겼을 문제 |
|---|---|---|
| "RAW는 10bit 선형" | 기본 RAW는 8bit **압축** 포맷 | 노이즈 모델 전체가 압축 아티팩트를 측정 |
| "Bayer는 RGGB" | 실제 **BGGR** (180° 장착 → 센서 반전) | 빨강·파랑 뒤바뀜, 렌즈 보정 테이블도 반대로 적용 |
| "게인 1.0 설정 가능" | 최소 **1.1228** | PTC 표에 존재하지 않는 조건을 기록 |
| "노출은 즉시 반영" | **5프레임 지연** | 브래킷 세트에 잘못된 노출 프레임 혼입 |
| "요청 노출 = 실제 노출" | 1 ms → 988 µs (−1.2%) | 합성 경계에 1% 단차 |

**원격 자동화** (`scripts/pi.sh`): PC에서 SSH로 Pi에 capture/를 동기화하고 실행한 뒤 결과를 회수한다. SSH ControlMaster로 연결을 재사용하고, 같은 이름의 결과가 있으면 덮어쓰지 않는다. Pi에서는 C++를 빌드하지 않는다(촬영 전용).

**자기 방어적인 촬영 코드**: 실제 RAW 포맷이 비압축(`*16`)이 아니면 촬영을 중단한다. 브래킷 프레임의 실제 노출이 2% 밖이면 버리고 다시 찍는다. 잘못된 데이터를 조용히 저장하는 것보다 실패하는 것이 낫다.

## 6. 범위 관리

- **한 번에 한 Phase.** 시작할 때 TODO, 끝날 때 수락 기준 결과 보고.
- **새 C++ 블록 순서**: Params(JSON 직렬화 + 기본값) → Python 기준 모델(해당 시) → C++ 구현 → 테스트 → CLI 노출.
- **일정이 밀리면 줄일 곳을 미리 정해 둔다**: Phase 4 NR 스윕은 고정값으로, Phase 5 QP는 2개로. **핵심인 Phase 2·3은 줄이지 않는다.**

## 7. C++ 코딩 규칙 요약

| 규칙 | 이유 |
|---|---|
| C++20, `namespace cctvlog` | 표준 기능(`std::span`, concepts 등)과 이름 충돌 방지 |
| 예외는 I/O·파싱 경계에서만 | 화소 루프 안에서는 예외 비용과 흐름 복잡도를 피함 |
| 버퍼는 `std::vector`/`unique_ptr`, 원시 포인터는 뷰만 | 소유권이 명확해 메모리 누수·이중 해제 방지 |
| `Image<T>`: row-major, interleaved, 명시적 stride | 외부 라이브러리(FFmpeg 프레임 등)와 메모리 공유, 캐시 친화 |
| 외부 수식은 주석에 출처 + 기준값 테스트 | 표준 식의 오타가 결론을 뒤집는 것을 막음 |
| clang-format | 리뷰를 형식이 아니라 내용에 집중 |

## 면접에서 설명하기

**30초 답변**
> "검증, 재현성, 하드웨어 실측 세 가지를 원칙으로 했습니다. 핵심 블록은 Python float64 기준 모델과 C++를 1e-5로 대조하고, 나머지는 상수·램프·체커보드 같은 해석적 입력으로 테스트했습니다. 의존성을 vcpkg baseline으로 고정하고 모든 실행에 git commit과 파라미터를 남겼고, 병렬화는 결정적으로 만들어 스레드 수와 무관하게 같은 해시가 나오게 했습니다. 하드웨어는 측정 스크립트로 먼저 확인했는데, 실제로 RAW 압축 포맷, Bayer 순서 반전, 최소 게인, 노출 지연을 잡아냈습니다."

**예상 질문**
- *Python과 C++를 왜 파일로만 연결했나요? pybind11이 더 빠르지 않나요?*
  → 중간 결과가 파일로 남아 검증과 디버깅이 쉽고, C++ 앱을 단독으로 재현할 수 있습니다. 이 프로젝트에서 병목은 파일 I/O가 아니라 화소 처리라서 바인딩의 이득이 작습니다. 확장 단계에서 필요하면 추가할 수 있게 경계를 단순하게 뒀습니다.
- *테스트가 제대로 동작하는지는 어떻게 아나요?*
  → npy 로더에 일부러 1비트 오류를 넣어 테스트가 실패하는지 확인했습니다. 실패해야 할 때 실패하는 테스트만 의미가 있습니다.
- *`-ffast-math`를 왜 금지했나요?*
  → 연산 순서를 바꾸고 NaN 처리를 생략해서, 기준 모델과의 정밀 비교와 실행 간 동일성이 깨집니다. 측정 프로젝트에서는 속도보다 결과의 신뢰성이 우선입니다.
- *문서와 실제 하드웨어가 다를 때 어떻게 했나요?*
  → 측정 스크립트로 확인하고, 원인까지 찾았습니다. 예를 들어 Bayer 순서가 다른 것을 발견하고 v4l2 컨트롤로 센서 반전 상태를 확인했습니다. 그 결과 렌즈 보정 테이블도 뒤집어야 한다는 결론을 미리 얻었습니다.
- *수락 기준을 못 맞추면요?*
  → 기준을 바꾸지 않습니다. 원인과 선택지를 결정 기록에 정리하고 결정한 뒤 진행합니다. 기준을 바꾸면 결과가 의미를 잃습니다.
