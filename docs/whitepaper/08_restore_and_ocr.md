# 8장. 복원 도구, 무결성, 번호판 평가

> 관련 Phase: 6(복원 도구와 번호판 평가) — ⏳ 예정

## 한 줄 요약
보관 영상의 가치는 "나중에 꺼내서 되살릴 수 있느냐"로 정해진다. 복원 도구는 파일이 바뀌지 않았는지 확인하고, 사이드카 정보로 곡선을 정확히 되돌리고, 하이라이트·섀도우를 다시 인화한다. 같은 입력이면 누가 언제 돌려도 **비트 단위로 같은 결과**를 낸다. 효과는 번호판 문자 인식률로 측정한다.

---

## 1. 쉬운 비유

- **SHA-256 = 파일의 지문.** 파일이 1비트만 바뀌어도 지문이 완전히 달라진다. 증거 영상이 녹화 후 손대지 않은 것인지 확인하는 방법이다.
- **역변환 = 원판에서 다시 인화하기.** 표시용 영상은 이미 인화한 사진이라 다시 밝게 하면 하얗게 날아간 부분은 그대로 하얗다. 보관 영상은 원판이라 창밖 번호판을 다시 꺼낼 수 있다.
- **레시피(recipe.json) = 요리법 기록.** 어떤 재료(입력 해시)로 어떤 순서와 양(파라미터)으로 만들었는지 남겨서, 다른 사람이 똑같이 만들 수 있게 한다.

---

## 2. 원리

### 2.1 복원 절차 (`apps/restore`)
```
INPUT.mp4 ──SHA-256 검증──▶ 디코드 ──▶ YCbCr→RGB ──▶ 역 H-Log LUT(사이드카의 곡선 파라미터)
    ──▶ 선형 HDR RGB ──▶ (옵션) 다중 프레임 평균 NR ──▶ 프리셋 톤/노출 ──▶ 8bit 출력
                                                         └ 예: highlight_recover (노출을 내려 하이라이트 복원)
```
출력 폴더에는 `recipe.json`(입력 해시, 파라미터, git commit, 라이브러리 버전)과 출력 해시가 남는다.

### 2.2 무결성: SHA-256
- 임의 길이 데이터 → 256bit 고정 길이 값. 같은 해시를 갖는 다른 파일을 일부러 만드는 것은 현재 기술로 사실상 불가능하다.
- 녹화 시 `*.sha256`을 함께 저장하고, 복원 시 먼저 검증한다. 맞지 않으면 처리하지 않는다.
- 감시 영상은 증거로 쓰일 수 있어서 "원본이 바뀌지 않았다"와 "이 처리 결과가 이 원본에서 나왔다"를 둘 다 보일 수 있어야 한다.

### 2.3 다중 프레임 평균 NR
- 정지 장면에서 N장을 평균하면 독립 노이즈는 σ/√N로 줄어든다. 16장이면 1/4(+12 dB).
- 한계: 압축 오차는 프레임끼리 **상관**될 수 있다. inter 예측이 이전 프레임을 참조하므로 같은 오차가 여러 프레임에 이어질 수 있다. 그러면 평균해도 √N만큼 줄지 않는다. 실제로 얼마나 주는지가 측정 대상이다.

### 2.4 결정성(determinism)
- 수락 기준: **스레드 1개와 N개의 출력 해시가 같다.**
- 부동소수점 덧셈은 결합법칙이 성립하지 않는다: (a + b) + c ≠ a + (b + c). 스레드가 합계를 나눠 더하면 순서에 따라 마지막 비트가 바뀐다.
- 그래서 출력에 영향을 주는 병렬 reduction을 금지하고, 행 단위 정적 분할만 쓴다(9장). 컴파일 옵션 `-ffast-math`도 같은 이유로 금지한다.

### 2.5 번호판 OCR 평가
- **문자 정확도**: 인식 결과와 정답 사이의 편집 거리(삽입·삭제·치환 횟수)로 계산한다. `정확도 = 1 − 편집거리 / 정답 길이`.
- 비교: 같은 장면에서 (a) 표시용 영상 vs (b) 보관 영상 + 복원 프리셋.
- OCR 엔진은 EasyOCR 또는 PaddleOCR 중 하나로 **버전을 고정**한다. 엔진이 바뀌면 숫자가 바뀐다.
- 공정성: 두 조건 모두 같은 ROI 자르기, 같은 전처리를 쓴다. 보관 쪽만 손으로 조정하지 않는다(프리셋 고정).

## 4. 엔지니어링 포인트

- **검증 먼저, 처리 나중**: 해시가 맞지 않으면 아무것도 출력하지 않는다. 잘못된 입력으로 그럴듯한 결과를 내는 것이 가장 위험하다.
- **복원에 필요한 모든 것은 사이드카에**: 곡선 이름과 파라미터 해시, 노출비, CCM, WB, NR 강도, 고정소수점 여부. 영상 파일만으로는 복원할 수 없게 설계되어 있으므로 사이드카가 1급 산출물이다.
- **recipe = 재현 가능한 처리 기록**: 입력 해시 + 파라미터 + 코드 버전(git commit) + 라이브러리 버전 → 출력 해시. 이 다섯 개가 같으면 출력이 같아야 하고, 그것을 테스트로 확인한다.
- **평가 도구 버전 고정**: OCR 같은 학습 모델은 버전마다 결과가 다르다. 실험의 일부로 고정하고 기록한다.

**30초 답변**
> "복원 도구는 SHA-256으로 원본을 먼저 검증하고, 사이드카의 곡선 파라미터로 역변환해서 선형 HDR로 되돌린 뒤 프리셋으로 다시 톤을 잡습니다. 입력 해시, 파라미터, git commit, 라이브러리 버전을 recipe로 남기고, 스레드 수와 무관하게 출력 해시가 같도록 결정적으로 구현했습니다. 효과는 인쇄 번호판 20장 이상을 강한 조명에서 찍어 표시용과 보관 복원의 OCR 문자 정확도로 비교했습니다."

**예상 질문**
- *왜 스레드 수에 따라 결과가 달라질 수 있나요?*
  → 부동소수점 덧셈은 순서에 따라 결과가 미세하게 달라집니다. 병렬 합계는 스레드 수에 따라 더하는 순서가 바뀌어서 마지막 비트가 바뀝니다. 출력에 영향을 주는 병렬 reduction을 쓰지 않고 행 단위로 독립 처리해서 해결했습니다.
- *해시가 같아야 하는 게 왜 중요한가요?*
  → 증거 영상은 제3자가 같은 처리를 다시 해서 같은 결과를 확인할 수 있어야 신뢰를 얻습니다. 비트 단위 동일성은 가장 강하고 자동 검사하기 쉬운 기준입니다.
- *다중 프레임 평균은 얼마나 효과가 있나요?*
  → 독립 노이즈면 √N배 줄지만, 압축 오차는 inter 예측 때문에 프레임끼리 상관될 수 있어 덜 줄어듭니다. 실측으로 확인할 부분입니다.
- *OCR 결과가 좋아지지 않으면요?*
  → 그것도 결론입니다. 어느 QP에서, 어떤 조명 조건에서 이득이 사라지는지를 보고합니다. 가설에 맞추려고 표시용 경로를 약하게 만들지 않는 것이 원칙입니다.
